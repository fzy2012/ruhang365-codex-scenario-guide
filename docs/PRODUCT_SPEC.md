# 产品规格：Codex Guide

## 1. 产品定义

Codex Guide 是一份持续更新、可核验、适合中文用户阅读的 Codex 使用指南。

它由三层共同组成：

1. **使用手册**：系统解释 Codex 的入口、能力、概念、操作方式、权限边界和常见问题；
2. **新功能说明**：把 OpenAI 官方变化转成经过人工核验的中文说明，解释变化、影响、使用方法和适用范围；
3. **快速查找交互**：用户可以按功能、问题、场景或搜索找到相关手册、更新和解决方案。

场景导航器是 Codex Guide 的一种交互入口，不是整个产品的定义。现有 8 场景 V1 应作为可复用原型迁入完整信息架构。

当前公开名称、仓库和永久链接暂时保持不变；产品改名和 URL 迁移必须另行决策并保护已有入口。

## 2. 可验收目标

一个不熟悉 Codex 的中文用户进入产品后，可以在不先阅读整套官方文档的情况下完成以下任一任务：

- 理解某个 Codex 功能是什么、适合谁；
- 按步骤完成一次具体操作；
- 查清近期某项官方变化及其影响；
- 描述自己的问题或场景，快速找到可信的解决方案；
- 看见来源、核验时间、适用范围和失败恢复，而不是得到未经证实的答案。

完成的判断不是“页面或功能已经开发”，而是代表性用户能从问题进入正确内容、完成关键操作并判断结果。

## 3. 目标用户

### 主要用户

- 第一次接触 Codex、不熟悉产品入口和术语的中文用户；
- 已经在使用 Codex，但需要查找具体操作或排查问题的桌面端用户；
- 需要了解近期新功能、变化范围和使用方式的普通用户、产品经理、运营人和开发者。

### 首期范围

- 优先服务 Codex 桌面端及与当前桌面端任务直接相关的能力；
- CLI、IDE、Cloud 等内容只有在官方证据、操作验证和维护能力就绪后进入正式手册；
- 不因为首期范围较窄，就把产品永久定义为“8 个场景导航器”。

## 4. 核心用户问题

产品必须能够承接四类明确意图：

1. **了解功能**：Codex 有什么？这个功能能解决什么问题？
2. **学习操作**：我要怎样完成某项操作？入口在哪里？步骤是什么？
3. **了解更新**：最近新增或改变了什么？对我是否可用？怎样尝试？
4. **解决问题**：我遇到了一个具体问题或场景，应该看哪篇内容、从哪一步开始？

无法可靠判断用户意图时，应要求补充产品形态、操作对象或预期结果，不得为了给答案而猜测。

## 5. 信息架构

### 5.1 使用手册

使用手册是产品内容底座，至少包含以下内容域：

- 入门与产品入口；
- 核心概念和术语；
- 项目、聊天、本地文件与上下文；
- 编写和约束任务；
- 文件修改、验证和结果检查；
- 权限、安全与授权边界；
- 自动化及其他经核验的高级能力；
- 常见问题与故障排查。

每篇手册至少包含：

- 一句话说明；
- 适合谁、什么时候使用；
- 前置条件和可用性范围；
- 操作入口与分步步骤；
- 示例；
- 成功结果；
- 常见失败与恢复；
- OpenAI 官方来源；
- 最近核验日期。

### 5.2 新功能说明

新功能说明不是自动转载的新闻流。每条公开内容至少回答：

- 发生了什么变化；
- 官方发布日期和来源；
- 涉及哪个 Codex 产品形态；
- 哪些用户可能受到影响；
- 在哪里找到、如何尝试；
- 相比原来有什么变化；
- 套餐、地区、工作区、操作系统或灰度限制；
- 影响了哪些手册或场景；
- 当前证据不能证明什么。

### 5.3 场景解决方案

场景页用于把用户问题连接到手册和更新内容。每个场景至少提供：

- 用户问题或目标；
- 推荐入口及原因；
- 分步操作；
- 可复制任务描述；
- 成功判断；
- 失败恢复；
- 相关手册；
- 相关新功能说明；
- 官方来源和核验时间。

同一事实应由统一内容源维护，场景页只做适合该问题的组合与呈现，不复制出无法同步的平行事实。

## 6. 浏览与查找

产品至少提供四种互补入口：

1. **搜索**：按自然语言、功能名和问题关键词查询全部已发布内容；
2. **按功能浏览**：沿使用手册目录逐层查找；
3. **按场景浏览**：从“我想完成什么”进入解决方案；
4. **查看最近更新**：按时间查看已经人工核验的新功能说明。

搜索结果必须区分内容类型，并展示标题、摘要、适用产品形态、最近核验时间和官方来源状态。

首期搜索可以使用确定性索引和关键词匹配，但必须覆盖全部已发布手册、更新说明和场景。未知查询应展示可解释的无结果状态或要求补充信息，不得静默推荐不相关内容。

## 7. 核心路径

### 查使用方法

```text
输入功能或问题
→ 查看匹配的手册与场景
→ 确认适用范围
→ 按步骤操作
→ 检查成功结果
→ 失败时恢复
```

### 看新功能

```text
进入最近更新
→ 查看已经人工核验的变化
→ 确认产品形态和可用范围
→ 阅读变化说明与操作方法
→ 跳转相关手册或场景
```

### 按场景找答案

```text
描述想做什么或遇到的问题
→ 获得匹配的解决方案
→ 查看相关手册和更新
→ 执行并判断结果
```

## 8. 内容与证据模型

正式内容至少记录以下字段：

- `id` 与稳定永久链接；
- `content_type`：manual、update 或 solution；
- `title`、`summary` 与正文；
- `product_surface`：Desktop、CLI、IDE、Cloud 或其他明确范围；
- `audience` 与 `prerequisites`；
- `official_sources`；
- `official_published_at`（来源明确提供时）；
- `verified_at`；
- `availability_scope`；
- `related_content_ids`；
- `status`：draft、pending_review、published、superseded；
- `limitations` 与不能证明的结论。

不得用抓取时间代替官方发布日期。来源未说明套餐、地区或灰度范围时必须标记未知，不得推断为所有用户可用。

## 9. 官方更新协议

```text
OpenAI 官方资料与 Changelog
→ 发现新增、修改或移除
→ 生成 pending_review 候选
→ 人工打开官方原文核验
→ 判断产品形态、可用范围和真实影响
→ 编写原创中文更新说明
→ 更新受影响的手册与场景关联
→ 运行内容、链接和交互验证
→ 经授权后发布
```

- 自动差异检测只能发现候选，不能自动生成公开事实；
- RSS 条目移除只表示当前快照不再包含该条目，不能直接解释为功能下线；
- 更新说明、手册修订和场景变化必须使用同一证据记录；
- 未经人工核验的候选不得进入搜索结果、最近更新或用户指南。

## 10. 版本路线

### 当前 V1：场景导航原型

已经具备：

- 8 个桌面端高频场景；
- 自然语言关键词匹配；
- 每个场景一个默认入口；
- 分步操作、可复制任务、成功判断和失败恢复；
- 官方更新 RSS 差异检测和 `pending_review` 候选。

当前 V1 不能被描述为完整使用手册或完整新功能说明产品。

### 下一阶段：Codex Guide 基础闭环

必须完成：

1. 建立 manual、update、solution 的统一内容模型；
2. 建立结构化使用手册目录和首批核心手册；
3. 把已核验更新生成用户可浏览的新功能说明；
4. 将现有 8 场景迁入统一内容模型，并关联相关手册；
5. 提供覆盖三类正式内容的搜索和筛选；
6. 为每篇内容展示官方来源、核验时间、适用范围和相关内容；
7. 保留现有公开链接，并为未来改名或迁移设计兼容入口。

### 后续扩展

- 扩展到经验证的 CLI、IDE、Cloud 内容；
- 增加内容修订历史和失效提示；
- 根据真实无结果查询和用户反馈补充手册与场景；
- 在不牺牲证据门禁的前提下改善搜索和个性化浏览。

## 11. 下一阶段验收标准

1. 用户可以从首页分别进入使用手册、最近更新和场景解决方案。
2. 搜索能够查询所有已发布的 manual、update 和 solution 内容，并区分内容类型。
3. 至少一组代表性核心手册形成从入口、步骤到成功判断和失败恢复的完整闭环。
4. 至少一条真实官方变化经过人工核验后形成公开更新说明，并关联受影响手册或场景。
5. 现有 8 场景全部迁入统一内容模型，永久入口不失效。
6. 每篇正式内容都有官方来源、核验日期、适用范围和限制说明。
7. 未知查询不猜答案；未审核更新不进入用户可见内容。
8. 桌面和 390×844 窄屏都能完成搜索、浏览、打开详情和返回。
9. 代表性新用户能够分别完成“查功能”“看更新”“解问题”三条任务。

## 12. 非目标

- OpenAI 官方文档的逐页镜像或机器翻译站；
- “AI 全流程项目共创”或通用项目执行平台；
- 自动抓取后直接发布的新闻流；
- 没有来源和适用范围的 AI 问答机器人；
- 为了内容规模一次覆盖所有 Codex 形态；
- 当前阶段建设账号体系、复杂 CMS、独立部署平台或第二套内容路由。
